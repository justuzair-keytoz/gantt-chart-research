# Spec — Roadmap Simulation (step model, scenarios, risk)

Synthesized from the CTO's [Planning Board and Roadmap Simulation](../../Planning%20Board%20and%20Roadmap%20Simulation.md) requirements doc, its `prototype.html`, the [competitor research](./01-feature-plan.md), and an ongoing grilling session that resolves the open questions between them, round by round. No new interview in this document itself — it's a synthesis of decisions already made; each round of questions happens in conversation, and only the resolution gets written here. Status: draft, first-pass ideation — expect this to keep changing shape as it gets built and tested against reality.

A note on scope: this repo has no issue tracker configured, so this spec lives as a markdown file rather than being filed as a ticket. Treat it the same way once a tracker exists.

## Problem Statement

A planning meeting today has no way to try a change before committing to it. A task has one status, one assignee, and a due date; when a date slips, nothing shows what else moves with it. Real work isn't one bar — a single task can run through planning, design, build, and release, with different people and different reviewers at each stage, each with their own stakeholders to keep informed. There's no way for a team to hold two competing versions of a plan open at once, argue over them, and commit to one with a record of why.

## Solution

Work breaks into Task → Stage → Step, where the step (not the task) is the thing that gets a date, an assignee, a reviewer, and a status. Any edit to the plan — a date move, a reassignment, a new dependency — opens a named scenario that holds only that change and everything it causes to move; the real plan is read-only until that scenario is committed. Several scenarios can exist side by side, compared on the same scorecard (slip, capacity, risk, readiness against contract dates), and committing one writes every one of its changes in a single transaction with a required reason, which lands as a Decision Record entry on every task it touched.

## User Stories

1. As a planning team member, I want to drag a step to a new date, so that I can see what the change actually costs before anyone commits to it.
2. As a planning team member, I want every downstream step, sprint, and risk to recompute the instant I make a change, so that I don't have to manually trace the consequences myself.
3. As a planning team member, I want my edits to live in a named scenario instead of the real plan, so that trying something doesn't put the team's actual schedule at risk.
4. As a planning team member, I want to hold two scenarios open at once and compare them side by side, so that the team can argue about real numbers instead of guesses.
5. As a planning team member, I want committing a scenario to require a one-line reason, so that the plan's history explains itself later.
6. As an individual contributor, I want to see what's mine to work on next and what's blocking it, so that I know what to pick up without asking around.
7. As a reviewer, I want to see what's waiting on my sign-off, with the handoff information next to it, so that I can review without chasing context.
8. As a project lead, I want to see where every piece of work sits across stages, so that I can spot what's aging before it becomes a problem.
9. As a stakeholder or exec, I want a stage-by-sprint view of risk, so that I know whether the release is on track without reading the whole plan.
10. As a tenant owner, I want to define which stages and steps exist for each project type, so that the team's process is enforced by the tool, not by memory.
11. As anyone looking at a task, I want to see exactly what's blocking it and what it's blocking, named in plain words, so that I don't have to interpret a line on a chart.
12. As anyone editing a step's date, I want the chain of steps inside its own task to re-time automatically, so that I never have to manually push every downstream step myself.
13. As anyone editing the plan, I want a step's dependency on another step in a different task to still be a real, visible constraint, so that cross-task work doesn't silently get out of sync.
14. As anyone adding a cross-task dependency, I want the tool to refuse a link that would create a cycle and tell me why, so that I can't accidentally build an unschedulable plan.
15. As a planning team member, I want to mark a person as out for a period and immediately see which contract risks become critical as a result, so that I can plan around absences before they cause a problem.
16. As a planning team member, I want to move the as-of date and see which warnings become expired, so that I can rehearse "what if we decide next week instead of today."
17. As a planning team member, I want to undo my last change in one action, even if that change cascaded to five other steps, so that experimenting doesn't feel risky.
18. As a planning team member, I want to reset a scenario back to the real plan, so that a dead-end idea costs nothing to abandon.
19. As anyone viewing the plan, I want a moved step to show where it used to be and by how many days it moved, so that the size of a change is visible at a glance, not just its end state.
20. As anyone viewing the plan, I want a step that lands on a non-working day because of a cascade to be flagged quietly, so that I notice it without it being treated as urgent as a contract risk.
21. As anyone viewing the plan, I want sprint boundaries and per-day capacity visible under the timeline, so that I can see overcommitment without opening a separate report.
22. As a planning team member, I want a sprint's own risk state to reflect whether its root-level tasks are still blocked, so that I don't have to check every task individually to know if the sprint is in trouble.
23. As an agent working over MCP, I want to read steps, people, scenarios, and risks, and create or edit a scenario under my owner's identity, so that I can assist with planning without being able to commit changes myself.
24. As a project member, I want only a person — never an agent acting alone — to commit a scenario, so that every change to the real plan has clear human accountability.
25. As anyone reading a task, I want its decision history to show the reason behind each change, including ones made by an agent, so that a resumed conversation doesn't start from zero.
26. As a planning team member, I want to quickly create a new task by name from right inside the Gantt, so that a piece of work that comes up mid-meeting doesn't require switching tools to add it first.
27. As anyone viewing the plan, I want the task and sprint names to stay visible while I scroll the timeline sideways, so that I don't lose track of what a bar belongs to when looking months ahead.
28. As a project lead, I want to expand or collapse every row at once, so that I can get an overview or drill into everything without clicking each row individually.
29. As a planning team member, I want to draw a dependency between two sprints or two tasks the same way I'd draw one between two steps, so that I don't have to learn a different gesture depending on what level I'm linking.

## Implementation Decisions

**Work model.** Task → Stage → Step, three levels. The step is the schedulable unit: its own start date, duration, assignee, reviewer, and stakeholder list. A task's own headline status/start/end are derived from its steps (roll-up, not stored independently), matching the pattern already confirmed in the competitor research (Jira's sprint-row status rollup) and reused here for both completion state and risk state.

**Steps are added on demand, not force-generated from the template.** A task starts as a single plain bar — identical to today's existing Gantt row. The step breakdown doesn't exist until someone deliberately adds one, via the same lightweight "add subitem" action (a `...` menu, matching the affordance found in Wrike), available from either a Task's row or a Sprint's row directly. The moment a step is added, the task expands into the parent/child structure (indented, collapsible) already confirmed across the competitor research (Jira, Wrike). The per-project-type template (R1/R2) still exists, but changes role: instead of silently stamping every new task with its full step list at creation, it becomes a one-click "add the standard Design steps" shortcut offered from the same add-subitem action. This keeps the consistency benefit the template exists for, without forcing step-level granularity onto tasks that don't need it, and keeps the common case (a simple task with no breakdown) exactly as visually clean as the Gantt view the original competitor research scoped.

**A minimal task-creation flow is in scope for slice one.** The same `...` menu offers "Add Task": prompts for a name, creates it, nothing more required up front (every other field — stage, assignee, dates — gets filled in afterward the normal way). This is in scope specifically because the Sprint-level add-subitem affordance above needs *something* to create when there's no existing task to attach a step to — rather than build a narrower, separate mechanism for that one case, the same general "Add Task" flow covers it, invoked from a Sprint's row instead of the toolbar. Created tasks are saved to the browser's local storage, layered on top of the fixed bootstrap fake data rather than mutating it in place — consistent with how the existing prototype already persists scenario state (`loadSaved`/`saveNow`).

**A newly created item's default placement depends on how it was created, not one universal rule.** A step added under an *existing* task with prior steps chains in after the last one, per R7's default — there's already a sequence to extend. A task created fresh under a *Sprint* (no prior steps to chain from) has nothing to chain to, so it's placed pinned to the start of that sprint's date range instead, and is freely draggable within it from there — the user positions it, the system just gives it a sane starting point rather than an arbitrary one.

**Drag-to-link is one interaction, available at every level of the gating hierarchy, not a step-only mechanism.** The existing prototype's link-drag gesture (`handleLink`) only operates between steps today. Since the gating relationship is already decided to be the same primitive at every scale (step↔step, task↔task, task↔sprint/milestone), the interaction for creating it should be the same gesture everywhere too — drag from one row's edge to another, whether both ends are steps, both are tasks, or one end is a task and the other a sprint or milestone. Building it step-only now and generalizing it later would mean redoing the same work twice.

**A task's stage path is locked at creation; the steps inside it are freely editable.** Once a task exists with a given sequence of stages, that sequence doesn't change — no retroactively inserting or removing a whole stage from a task that may already have scheduled or completed steps in it. Steps *within* the existing path can be freely added, removed, retimed, reassigned. If a task genuinely needs a stage it wasn't created with, the answer is a new task with the right path, not stage surgery on a live one — letting a stage be inserted mid-flight creates real scheduling ambiguity (where do its steps land relative to work that's already dated or done) that nothing in either source doc named a need to solve.

**Dependencies are one relationship, reused at three scales.** A single directed "X gates Y" edge type, scoped by what's on each end:
- Step → next step in the same task's chain: fixed by default, re-timeable but never unlinkable (the chain itself can't be broken, only moved).
- Task → task: a cross-task link, surfaced to the user as named "Blocked by" / "Blocking" fields on the task (not a generic "dependency" label) — the clearest, most repeated finding across the competitor research (Jira, ClickUp, Wrike, Linear all converge on naming the relationship explicitly). The existing prototype already builds this functionally — its step editor has separate "Depends on" and "Blocks" lists with add/remove — it just needs the labels renamed to match the decided vocabulary; no new mechanism required.
- Root-level task(s) → sprint or milestone: the task "gates" the container. One-directional by construction — a sprint or milestone has no outgoing gates of its own, which means a cycle structurally cannot form at this layer; cycle prevention (refuse + explain, per the step/task layers) is not needed here for free, not by extra logic.

A sprint's or milestone's own risk state is a rollup of whether its gating tasks still have an open gate against them — same mechanism as the status rollup, applied to risk instead of completion.

**Milestones render as a diamond with connector lines**, not a plain vertical dated line. Each task that gates a milestone draws a dashed connector to it, adapted directly from Airtable's milestone rendering — more legible than a line, with no change to the underlying one-directional "gates" semantics.

**Sprints become real, collapsible rows in the row list, with a sticky label column independent of horizontal scroll.** Today's prototype only draws a sprint as a background band and an axis label — there's no sprint *row* to collapse, roll a status up onto, or hang the add-subitem menu off of. The row/label column (task names, sprint names, step names) needs to stay pinned while the date grid underneath scrolls horizontally, matching the Airtable and Wrike screenshots referenced — otherwise "what does this bar belong to" is lost the moment someone scrolls right to see a date three months out. The toolbar gets two more actions to match: **Expand all / Collapse all** (operating on every row in the tree at once, not just one at a time) and an explicit **Add Milestone** action sitting next to Add Task — both pinned at the top of the sticky column, same placement Airtable uses for its "+ Add record" / "⚑ Add milestone" pair, renamed to this product's own vocabulary.

**The dependency-line-turns-red-on-conflict pattern (Airtable) does not transfer to this engine, and that's deliberate, not an oversight.** Airtable needs that check because its predecessor/successor link is soft — nothing enforces it, so it can drift out of sync and needs a watchdog. This engine's scheduler enforces the step chain on every recompute (a step cannot start before the day after its dependency ends), so the state that check exists to catch cannot occur here. No equivalent was substituted; forcing one in would be solving a problem this architecture doesn't have.

**Scenarios are the only way to edit.** The real plan is read-only; the first edit (or an explicit "new scenario" action) opens a named scenario holding only the diff from baseline. Within a scenario, every edit — including mid-drag — recomputes all dependent dates, sprint membership, risk, and workload live, with no per-edit confirmation. The single point of confirmation is Commit: one action, requires a reason, writes every changed task in one transaction (all-or-nothing — a partially applied commit is treated as a failure state, not a partial success), and appends that reason as a Decision Record entry on each task it touched.

**Committing a scenario warns before discarding any sibling scenario that hasn't itself been committed.** The baseline moves the moment one scenario commits, which makes every other open scenario's diff describe a world that no longer exists. Found as a gap in the existing prototype, which silently wipes every other scenario back to a fresh baseline the instant any one commits — a team could lose a second scenario's work mid-meeting with no warning. The fix is the same UI shape already proven for cascades (Wrike's "Apply the rules of date alignment?" — name the consequence, let the user confirm or cancel), applied here to a different trigger: "Committing *this scenario* will discard *that scenario*, which hasn't been committed. Continue?" Rebasing the sibling onto the new baseline instead of discarding it was considered and rejected for slice one — real engineering complexity (correctly replaying arbitrary edits against a changed baseline) that isn't justified yet; a warning is cheap and prevents the actual failure mode (silent data loss), which is the part that matters now.

**Undo is atomic per user action, cascade included.** If one drag pushes five downstream steps, one undo reverts all six. Forcing the user to undo each cascaded step individually would punish them for the cascade working correctly.

**Concurrency: no shared real-time editing of a single scenario.** Multiple people wanting to try different ideas each open their own scenario and compare — that's already the mechanism the requirements doc names as the reason scenarios exist ("the team needs two alternatives open while they argue"). Building live multiplayer editing into one shared scenario (presence, conflict resolution, operational transforms) solves a problem the Compare view already solves a different way, for a surface that's draft/scratch data until committed.

**Recompute runs in three places, reusing the pattern this codebase already has for the same underlying problem.** `packages/calculated-fields` runs one shared evaluation package in three contexts (ADR-002): the UI compiles/previews live without persisting, Strapi runs it synchronously as the authoritative write during normal mutation, and Temporal re-runs it async as a daily catch-up for drift that happens without any edit (e.g., a date-relative formula aging past a threshold). The scheduling/risk engine follows the same shape: client-side live recompute during editing (non-persisted, exactly what slice one builds), server-side synchronous recompute as the authoritative write on Commit (slice two), and a daily Temporal tick re-evaluating risk severity against the current date so a warning can become expired overnight without anyone opening the plan (slice two, needed for R19's "as of a date" requirement to hold even when nobody's actively editing). This isn't a new architectural decision — it's the same one already made for calculated fields, applied to a structurally identical problem.

**Risk severity has four tiers: critical, warning, expired, informational.** Critical/warning/expired already get both an inline colored outline on the step bar and a line in the risk panel. Informational findings get a quiet inline marker — a small dot, not a colored outline — plus a panel entry. The inline treatment exists because the reason this category of finding is worth adding at all is that it's useful precisely when seen in passing, not when hunted for in a panel; but it must not visually compete with the three higher severities, which need to read as more urgent at a glance.

**The weekend-landing flag fires on a precise condition, not "this step's span happens to touch a weekend."** Almost every multi-day step crosses a Saturday or Sunday somewhere in its range — flagging on that would be constant, meaningless noise. The actual trigger: the step's **start or end date itself** lands on a non-working day, **and** the step is currently flagged `moved` within the active scenario. The second half of that condition matters as much as the first — it scopes the flag to "this just became true because of something you did," not a standing property of baseline data nobody's touching.

**Duration and cascade math run in working days; contractual deadlines stay in calendar days.** A weekend doesn't silently extend a task's visible duration, but a contract clock (LC notice, COD) doesn't pause for one either. The prototype currently mixes these inconsistently (calendar days for duration, weekdays for capacity) — this is the fix.

**A step belongs to whichever sprint its own end date falls in — not whichever sprint its parent task is "assigned to."** A task whose steps span two sprints simply appears, in pieces, on both sprint boards, and each sprint's velocity counts only the steps that actually finished inside it. The alternative (keep the whole task on one board for tidiness) breaks the per-person-per-day capacity math, which has no way to represent partial-task completion within a sprint.

**Editing (drag-to-reschedule) is in scope from the first shippable slice, not deferred to a read-only version first.** The entire value of "see everything that moves" depends on direct manipulation; a read-only version is just the earlier, smaller Gantt-as-third-view idea again.

## Testing Decisions

- The scheduling core (topological ordering, cycle detection, recompute-on-change) should be tested as pure functions, independent of any UI — given a task graph and an edit, assert the resulting dates, sprint memberships, and risk findings, without rendering anything. This is the highest-value, lowest-cost test surface in the whole feature: it's deterministic, has no I/O, and almost everything else (rendering, the risk panel, the comparison table) is a direct function of its output.
- Scenario commit should be tested for atomicity specifically: assert that a failure partway through a multi-task commit leaves zero tasks changed, not some.
- Cross-task dependency cycle prevention should be tested with an explicit "attempt to create a cycle" case per layer (step-to-step across tasks, task-to-task) and assert both the refusal and that the reason given names the specific cycle.
- The multi-sprint step-splitting behavior (a task's steps landing in different sprints) should have its own test: assert that each sprint's velocity counts only its own steps, not the whole task.
- No existing test prior art in this repo for this feature's domain — this is new ground, not an extension of an existing tested module. Once a scheduling engine exists, its test shape should match how `ruleengine/`'s own rule-evaluation tests are structured, for consistency with the rest of the codebase's conflict-detection moat, since this risk system is explicitly meant to reuse that same evaluate-and-surface lifecycle.

## Out of Scope

- The 3D and 4D rendering surfaces in the prototype (explicitly deferred by the user; the flat Gantt is the surface this spec targets).
- Typed dependency relationships beyond finish-to-start (start-to-start, finish-to-finish, start-to-finish) and lead/lag offsets between steps — every competitor surveyed treats these as secondary, and nothing in the grilling session named a need for them.
- The Decision Record's *backend* subsystem — exact file format, repository mirror location convention, reference-copy storage, MCP read/write wire format. Real, specified in the source requirements doc, deferred to slice two. This is distinct from the change/decision trail itself: showing "what changed and why" inside the prototype (a commit's reason, a scenario's list of changes) is part of proving the mechanics in slice one; writing that trail to a real, immutable, git-mirrorable, MCP-readable record is backend wiring and belongs in slice two.
- A second, lighter-density timeline view alongside the main Gantt (the Wrike/Smartsheet/Airtable "two views" pattern from the research) — real pattern, not needed for a first slice.
- Baseline-vs-actual variance tracking (Smartsheet's strongest standalone finding) — a genuinely good, separate idea, answering a different question than this spec covers.
- Where availability data comes from beyond a manually entered "out" period, and the step templates per project type — both explicitly deferred in the source requirements doc.
- Role-based views (R33 — the separate IC / reviewer / lead / exec / tenant-owner lenses on the same plan) and agent/MCP read access (R34). Neither exists in the prototype; neither is slice one or two as scoped in this document. Named explicitly here so it isn't silently assumed to be covered.

## Permissions

**Editing a task's ad hoc step list gates on the existing `tasks.manage` capability** (`role-capability`/`capability`, seeded in `scripts/seed-role-capabilities.js`) — the same capability that already governs general task mutation in this codebase, reused rather than introducing a new permission tier. **Editing the per-project-type step template** (R1, tenant-owner-maintained) is a level above that — scoped to the tenant-owner/admin role, not available to every task-manager. The distinction matters because one is a local, reversible decision about a single piece of work, and the other changes the process for every future task of that type.

This is the intended design for once the feature is wired to real data — **not a requirement for slice one** (below). A frontend-only prototype on fake data has no real auth to gate in the first place; permissioning gets built when the backend wiring happens, not before. Documented now so it isn't forgotten or re-litigated later.

## Slicing

**Slice one proves the engine, entirely on the frontend, before anything touches a backend.** The cascade/scheduling engine, the scenario model, the comparator (multi-scenario side-by-side), and the change/decision trail all need to be built and validated as a self-contained prototype — the same shape as the existing `prototype.html`, refined to match every decision in this spec — running on fake data, no Strapi integration, no persistence beyond the browser, no MCP, no permission enforcement. The goal of slice one is confidence that the mechanics are right: that cascades compute correctly, that comparing two scenarios produces numbers people trust, that committing writes a trail that actually explains itself. None of that requires a real task, a real database write, or a real person's auth token to prove.

**Slice two is backend wiring**, not new mechanics: connect the proven engine to real Strapi task data, make commits real writes, make the Decision Record entries real and MCP-readable, and turn on the permissions decided above. Nothing about the engine's design should need to change at that point if slice one did its job — slice two is integration, not redesign.

This also reframes the earlier "does slice one include compare" question from the previous round: the split isn't single-scenario-vs-compare, it's prototype-vs-backend. Compare belongs in slice one, because it's part of proving the mechanics work, not part of what requires real infrastructure to exist.

## Further Notes

This spec reconciles two documents that started at different scales: the original competitor research (docs `00`/`01` in this folder) scoped a single flat Gantt view sitting next to Table and Kanban; the CTO's requirements doc is a much larger three-level work model plus a full scenario engine plus a standalone audit-trail subsystem. The decision made in this grilling session was to treat the larger doc as the real target, not a someday-vision, and to sequence the work into slices rather than shrink the scope back down.

Every open item from the grilling session is now resolved and reflected as a decision above: named relationships, the gating hierarchy, milestone rendering, cascade/commit/undo semantics, concurrency, severity tiers, the working/calendar day split, multi-sprint step ownership, step-edit permissions, the slice-one/slice-two boundary, where recompute runs, on-demand step creation, stage-path mutability, what happens to sibling scenarios on commit, minimal task creation, default placement for newly created items, the sticky sidebar and collapsible sprint rows, and the exact trigger for the weekend-landing flag.

One reversal worth calling out rather than burying: an earlier round scoped task creation entirely out of slice one, reasoning that it belonged to Table/Kanban, not the Gantt. That got overturned once the Sprint-level add-subitem decision needed *something* to create and a narrower, separate mechanism for just that case would have been more work than just allowing task creation generally. Noted here because it's a real example of a decision changing shape once a later decision exposed what it actually required — exactly the kind of thing this document expects to keep happening.

This is a first pass at ideation, not a locked spec — expect this to keep changing shape as the ideas get built and tested against reality. Treat each decision above as the current best answer, not a commitment no one's allowed to revisit.
