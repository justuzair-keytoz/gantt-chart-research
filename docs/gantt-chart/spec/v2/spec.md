## Unchanged from v1

## Problem Statement

Carried forward from v1, unchanged: a planning meeting has no way to try a change before committing to it, and when a date slips, nothing shows what else moves with it (see `v1/spec.md`'s own Problem Statement for the full statement).

v2 adds a second problem, surfaced by actually showing the v1 build to its first outside viewer: **the tool doesn't yet explain itself.** The PM who saw it for the first time called it "too complex" (DECIDED — this is a direct quote of feedback given, not a summary). Two underlying code-level issues were found to be most of the cause of that reaction, plus everything else raised:

- **A sprint is drawn twice.** `buildRows()` in `app/src/components/FlatGantt/layout.ts` puts task rows under a sprint row, and the X axis is also calendar time. A task whose steps end in different sprints appears split across several sprint groups, each only showing the steps that happen to end there — which is also, directly, [`Planning Board and Roadmap Simulation.md`](../../../../Planning%20Board%20and%20Roadmap%20Simulation.md)'s R6 ("a step belongs to the sprint its end date falls in") plus its own explicitly unresolved follow-up question ("Deferred to planning simulation": *"How a task whose steps end in different sprints appears on each sprint's board and counts toward velocity, within R6"*) — the CTO doc named this exact gap and deferred it; v1 inherited the deferral without ever resolving it, and the resulting multi-sprint-task confusion is one of this round's loudest feedback items.
- **The engine knows more than the UI says.** `computeSchedule()` already tracks `pushedBy`, `outHit`, and `slip` per step — the actual cause of why a date landed where it did. The UI surfaces none of it directly: a ghost bar, a colored outline, and side panels are the only signals, none of which say *why* in words.

The full raw feedback list, kept verbatim (item 2 was cut off mid-sentence in the original feedback session, at "why does…", and clarified in follow-up — see the clarification folded into its User Story below):

1. Too complex to understand.
2. Reason for timeline change (why a certain task is dependent, why does [a deadline change or extension happen] — clarified in follow-up: a reason understandable by someone *viewing* the chart, not just a system log).
3. Huge tasks: how the milestone feature can work if a task isn't bounded to a sprint or a single milestone — how can it be tracked so people understand it spans multiple sprints, without being confined the way it is today.
4. Flatten the bars into parents upon expand/collapse, based on the level of expand or collapse — the underlying bars should flatten into a single parent bar.
5. Limitations of subtasks (same underlying cause as #4).
6. Multiple reporters: a list of people to contact for a task.
7. Pinch-to-zoom in/out on a MacBook trackpad — the Next.js port has no zoom at all; the original prototype preserved this behavior.

**Principle governing this round (DECIDED, stated directly):** build around how users actually work; don't adapt users to the tool. Aim for something none of the competitors researched in this repo already do.

## Solution

Four code-level reversals (named formally in Further Notes below) plus four new interaction mechanisms, aimed at the two root causes above:

1. Sprints stop being a second, competing grouping axis for bars — DECIDED: sprints render as highlighted bands on the calendar header, the way the original prototype did it, with flat bars underneath. Whether a sprint *row* also still exists in the tree alongside the band is OPEN (see Open Questions) — the user's messages imply yes, but this was never directly confirmed.
2. Nesting goes to any depth, DECIDED, with a collapsed parent flattening its descendants into rolled-up segments inside its own row (PROPOSED design: see "Rolled-up segments" below) rather than showing nothing.
3. Every schedule-driven date gets an attached, human-readable reason, and a cascaded step inherits the reason that caused its own push, visible on hover and in a task's history (PROPOSED design: see "The reason model" below) — the *need* for this is DECIDED; the chip/inheritance/Decision-Record mechanics are not yet confirmed.
4. "Blocked" is split into the several distinct business rules the project owner actually named (DECIDED), each producing its own plain-English sentence, replacing the single ad hoc "critical gate violation" check that is currently the only thing capable of turning a line red.

## User Stories

Numbered continuing from v1's 29. Each follows the existing "As a... I want... so that..." shape.

30. As anyone viewing the plan, I want a collapsed parent row to still show its children's work as rolled-up segments inside it, so that collapsing something doesn't make its progress disappear.
31. As a project lead, I want "Expand all" available at every row's own level, not only globally, so that I can drill into one branch of the tree without opening everything else.
32. As anyone viewing the plan, I want my expand/collapse choices remembered across visits, so that I don't have to re-set up the view I was working in every time I open the chart.
33. As anyone viewing the plan, I want sprints shown as bands on the calendar itself, so that a task's real duration is visible without needing the sprint to also be a container I must open.
34. As a planning team member, I want a task that runs longer than its sprint or milestone to still render as one continuous bar that visibly crosses the boundary, so that "this work is bigger than one sprint" is something I can see instead of something the tool hides by splitting the task up.
35. As anyone viewing the plan, I want to see, in plain words, why a date is what it is — which step or person it's waiting on — so that I don't have to reverse-engineer the schedule from a ghost bar and an outline color.
36. As anyone viewing the plan, I want to ask "why can't I move this?" and get a specific answer naming the rule and the task it conflicts with, so that a frozen drag doesn't feel like an unexplained wall.
37. As a planning team member, I want "blocked" to cover the actual ways work gets stuck — a clashing assignee, unowned overlapping work, or a dependent subtask whose predecessor hasn't reached a handoff point — not just a missed deadline, so that the tool reflects how blocking actually happens on this team.
38. As a reviewer, I want to see the handoff point a predecessor step must reach before my step can start, so that I know when I can realistically begin, not just that I'm "after" someone else.
39. As anyone viewing the plan, I want a dependency declared at the stage or sprint level to apply to every step inside it, so that I don't have to redraw the same link for each individual step.
40. As anyone looking at a blocked task, I want to see who to contact about it, so that I know who to reach when I hit the same blocker.
41. As anyone viewing the plan on a trackpad, I want to pinch to zoom in and out the way the original prototype supported, so that switching between an overview and a detailed view doesn't require a tool I don't have.

## Implementation Decisions

**Nesting goes to any depth (DECIDED).** v1's fixed Task → Stage → Step, three levels, chain-locked, is reversed for the nesting *depth* specifically — see Further Notes for exactly what this reverses and what it keeps. A subtask can itself have subtasks, to whatever depth a user actually creates. Expand/collapse and an "Expand all" control exist per row, at every level, not just once globally for the whole tree (DECIDED). Expand/collapse state is saved to `localStorage`, per the existing precedent (`useRoadmapStore.ts`'s `expanded` array is already persisted this way for sprint/task rows) — extending the *same* field to arbitrary depth, not a new mechanism. **BUILT (2026-10-21, see `CHANGELOG.md`):** the recursive tree and per-row "Expand all" — `TaskDef` gained `parentTaskId: string | null`, `app/src/lib/engine/schedule.ts`'s task-rollup and `app/src/components/FlatGantt/layout.ts`'s `buildRows()` both recurse through it to arbitrary depth (a parent with children, with or without its own steps, rolls up to span them; a `visited`/`visiting` set guards against a corrupt cyclic chain), and every collapsible row — at every depth — now gets a second, per-row "Expand all beneath this row" affordance (`collapsibleDescendantIds()` + the store's new `expandSubtree()`, which merges rather than replaces `expanded`) alongside its existing +/− toggle and the untouched global "Expand all" button. One small illustrative example (`OAK-200` → `OAK-201` → `OAK-202`, depth 2) was added to the mock dataset. Explicitly NOT built: **rolled-up segments on collapse** (User Story 30, see its own PROPOSED entry below) — a parent task with children behaves exactly like today's uid-less collapsed row (no bar), same as a plain-bar task with no uid does today, not the fancier merged-segments version. Not verified in a running browser — reasoned through only; see the changelog entry's "Not verified" note (whether the three-level example actually renders/collapses/expands correctly, and whether a returning user's pre-existing persisted `expanded` array round-trips cleanly against the new deeper row ids, are both called out there as unchecked).

**Stages stay (DECIDED), including stage-level dependency.** [`Planning Board and Roadmap Simulation.md`](../../../../Planning%20Board%20and%20Roadmap%20Simulation.md)'s R1 and R2 require a task to travel an ordered, tenant-owner-maintained list of stages per project type — this is a CTO requirement, not an open design choice, and the project owner independently confirmed it directly ("we have multiple stages, and development stage may have a dependency on design and review phase before that"). A dependency declared at the stage level expands into real edges between the gating stages' last steps and the dependent stage's first step (PROPOSED mechanism — see "Stage-level dependencies expand into step edges" below); the stage-as-a-concept staying is DECIDED, the exact expansion mechanism is not yet built or confirmed against a real multi-predecessor case.

**Sprints render as calendar bands, flat bars underneath (DECIDED).** The original prototype's own approach — sprints highlighted directly on the calendar timeline, not as a container row a task must belong to — is confirmed as the direction, explicitly because it resolves the "huge task spanning multiple sprints" feedback that no competitor researched in this repo's `competitors/` folder solves either (see the Jira citation in this round's research update, which only gets as far as inferring a parent's dates from its children and warning on overrun, not actually letting a bar cross a container boundary cleanly). This directly reverses v1's "a step belongs to the sprint its end date falls in" / sprints-as-collapsible-container-rows pair — see Further Notes for the formal reversal note. **OPEN, not decided:** whether a sprint still also exists as a collapsible row in the tree, in addition to the calendar band. The user's messages lean toward "yes, both," but this was never asked and confirmed directly — treat it as unresolved until it is. **BUILT (2026-10-21, see `CHANGELOG.md`):** the additive-band half only — a tinted full-height column band plus name label per real sprint, drawn on the calendar directly (`app/src/components/FlatGantt/FlatGantt.tsx`'s `sprintBands`, painted underneath weekend shading, row highlights, milestones, bars, and links, same convention as the existing `weekendBands`), alternating colors ported from `prototype/app.js`'s own sprint-axis rendering, recomputed against the live zoom `dw` state the same way `weekendBands` already is. Explicitly NOT built: the OPEN row question above — `buildRows()`'s existing sprint-row grouping/collapsing in `layout.ts` was read but not touched. Not verified in a running browser — reasoned through only, see the changelog entry's "Not verified" note (band/row-highlight color coincidence, label clipping at zoom extremes, and later-row label collisions are all called out there as unchecked).

**A task bigger than a sprint or milestone needs no special handling once sprints are bands (DECIDED, follows from the above).** It's simply a bar whose span crosses one or more band boundaries, same as any other bar — PROPOSED addition: a small tick mark where the bar crosses each boundary, so the crossing itself is visible at a glance, not just inferable from the bar's length (not yet confirmed).

**The reason model (PROPOSED, not confirmed).** Two distinct kinds of "why," per the project owner's own clarification that feedback item #2 meant something a *viewer* could read, not a system log entry:
- A human-written reason attached to a schedule change: a short, fixed set of chips (scope grew, waiting on someone, person was out, estimate was wrong, priority changed, other-plus-text), required only when the change crosses a hard edge (a milestone) or creates a clash, otherwise optional and shown as "No reason given" if skipped rather than blocking the edit.
- A knock-on reason: a step pushed by someone else's change inherits that change's reason via a `causedBy` reference, so a downstream step's tooltip can read "Pushed +3d by Design review (waiting on lender docs, Sam, 20 Oct)" instead of just showing that it moved.
Both would be stored as Decision Record entries, reusing the existing entry shape (`why`, `when`, `n`) with two additions: a `kind: "schedule change"` discriminator and the `causedBy` reference. This reuses the existing record mechanism rather than introducing a second one, which is consistent with how v1 already extends the Decision Record for commit reasons — but the chip set, the "required past a hard edge" rule, and the `causedBy` inheritance chain are design, not yet decided or built.

**Rolled-up segments on collapse (PROPOSED, not confirmed).** A collapsed task shows its children's actual segments inside its own row — not one earliest-start-to-latest-end summary bar (which would hide gaps between children), and not nothing (today's behavior, see Baseline Fixes below). Overlapping child segments merge visually; a crowded group (many children, little room) instead shows a single state-colored bar plus a short summary like "6 tasks, 2 blocked." This is the shape named in this round's research as Microsoft Project's "roll-up Gantt bars" pattern (see the new `competitors/ms-project.md` citation) — evidence is documentation, not a screenshot, flagged as such in that file. The merge/crowding threshold and the exact segment-rendering rules are not yet designed in detail.

**The generic tree uses `parentTask`/`subtasks` (DECIDED 2026-10-21).** Confirmed directly by the project owner: Gantt nesting reuses the same `parentTask`/`subtasks` relation Table and Kanban already populate — a task's existing subtasks show up in the Gantt automatically, not a separate, parallel nesting layer that happens to reuse the same field shape. This settles the OPEN question v1's `data-shape-mapping.md` had raised (it deliberately avoided this relation for the Step concept, reasoning it conflated a generic nesting mechanism with the specific three-level Task → Stage → Step model) and verified directly against the real schema this round (`databonder-enterprise-search/Strapi/src/api/task/content-types/task/schema.json`, read-only, not edited): `parentTask` (manyToOne) / `subtasks` (oneToMany), both targeting `api::task.task`, exist exactly as described.

**Consequence of the above, for this app's mock/prototype engine specifically:** `databonder`'s real schema decision doesn't automatically tell this fake-data prototype how to model it, since `app/`'s engine has no Strapi relations at all today — only its own `TaskDef`/`Step` shapes. The decision does settle the *semantics* to build toward: a task can have child tasks, recursively, each a full task in its own right (not a different, lesser kind of node) — not a Step-shaped thing nesting inside a Task-shaped thing. The exact mock-data representation (e.g. an optional `parentTaskId` on `TaskDef`, recursed over in `buildRows()`) is implementation, not a further open decision — this paragraph exists so building it doesn't get blocked re-litigating what's already settled above. **BUILT (2026-10-21, see `CHANGELOG.md`):** exactly as previewed — `parentTaskId: string | null` on `TaskDef`, recursed over in both `schedule.ts`'s task-rollup and `layout.ts`'s `buildRows()`.

**"Blocked" is several distinct rules, not one check (DECIDED to exist as multiple rules; the rule table itself is PROPOSED).** The project owner named three concrete meanings directly: an assignee has clashing deadlines across their own work; nobody is assigned, but timelines overlap with other work; and dependent subtasks with different people, where the first must reach a certain point before the second can start. A PROPOSED rule table turns each named meaning (plus two already-latent-in-the-engine cases — a predecessor that isn't done, and a stage-order violation) into one row: the condition that fires it, whether it blocks the move outright, warns and allows with a required reason, or just surfaces a flag — see the table in "Blocked rules" below. A generated legend and the "why can't I move this?" message would read from the same table, so the three surfaces can't drift out of sync with each other. None of this is built or confirmed in detail; the need for multiple distinct rules is what's actually decided.

**Blocked rules (PROPOSED table, not confirmed):**

| Rule | Fires when | Exists in v1 today? |
| --- | --- | --- |
| Waiting on predecessor | A predecessor step isn't marked done | No — v1's `done: end < asOf` (`schedule.ts`) is a date comparison, not a task-status check (verified by reading the code this round) |
| Person clash | Same person assigned to overlapping work | Only visible in the Workload panel; not reflected on the bar itself |
| Unowned overlap | No assignee, and dates overlap other work | No unassigned state exists today |
| Handoff not ready | A dependent step starts before its predecessor reaches a named checkpoint | Not modeled — see "Handoff" below |
| Past hard deadline | A task ends after its gating milestone | Yes (v1's drag-cap + broken-red outline). **BUILT (2026-10-21, see `CHANGELOG.md`):** the owner's mockup showed this state as a solid diagonal-hatch fill across the whole bar, not just an outline — `Bar.tsx` now layers a red `crithatch` SVG pattern (own pattern, not a reuse of the existing `revhatch` review-step hatch, so the two stay distinguishable when a step is both a review step and past-deadline at once) on top of the bar when `outline === "critical" \| "expired"`. The existing dashed outline was kept, not replaced — this is additive styling on the same, unchanged detection logic. This is *styling only*; it is explicitly not the "Spill" row below, which still needs the commitment/position data-model split and is not started. |
| Spill | A task's position runs past its committed sprint band | Only as an automatic sprint-reassignment, not a visible "spilled but still committed" state — see Further Notes' reversal note |
| Stage order | A stage starts before a stage it depends on finishes | Only enforced inside one task's own chain today, not across declared stage-level dependencies |

Each rule would carry one of three behaviors — block the move outright, warn and allow with a required reason, or surface a flag without blocking — per rule, not uniformly. Not yet assigned per-rule; PROPOSED shape only.

**Handoff as a checkpoint (PROPOSED, not confirmed — answers one OPEN question with a direction, not a decision).** Rather than inventing a new dependency type, a predecessor step with a handoff requirement would be split into two parts, and the dependent step's link points at the first part ("Wireframes approved") instead of the whole step. This needs the nesting-to-any-depth mechanism above to exist first, and doesn't require new engine concepts beyond "a step can itself have steps." Whether the handoff point is a named checkpoint (this proposal), a percentage, or a fixed number of days is explicitly OPEN — this proposal answers it with a direction, it does not settle it.

**Stage-level dependencies expand into step edges (PROPOSED, not confirmed).** A dependency declared as "Development depends on Design and Review" would expand into real edges from the last step of each of those stages to the first step of Development, reusing the existing step-to-step gating primitive rather than inventing a stage-level dependency type. This is the same shape the research below cites for Microsoft Project's summary-task-predecessor behavior (a summary task's predecessor limits when its subtasks can be scheduled) — evidence is documentation, not a screenshot. Multi-predecessor expansion (what happens when a stage has more than one gating stage, each contributing a different step) is not yet designed against a concrete case.

**Contacts, not "reporters" (PROPOSED naming, DECIDED need).** The project owner's own framing was explicitly experimental: a list of people to contact about a task so whoever hits a blocker knows who to reach — not Jira's "reporter" meaning (who raised the issue). A single People section per task — Assignee (one), Reviewer (zero or one, unchanged from v1), Contacts (many) — would replace the free-text `stakeholders` concept rather than sit alongside it as a fourth, overlapping idea; Contacts inherited down the tree and surfaced specifically on the "why"/blocked card (PROPOSED placement, not yet confirmed) is the only place it would show. v1's own `data-shape-mapping.md` already flagged an open question — whether `watchers` and `stakeholders` are the same concept — this round doesn't resolve that either; it adds Contacts as a third candidate name into the same unresolved space. The project owner was explicitly open to alternative naming/suggestions here, not committed to "Contacts" as final.

**Pinch-to-zoom is required, continuous zoom with presets is proposed.** DECIDED: zoom must work on a MacBook trackpad, matching the original prototype's behavior, which the Next.js port currently has none of at all (`DW` is a hardcoded constant, `36`, imported everywhere it's used — verified this round). **BUILT (2026-10-21, see `CHANGELOG.md`):** the DECIDED half — `DW` is now React state (`app/src/components/FlatGantt/FlatGantt.tsx`), continuous zoom via ctrl/meta+wheel (how a trackpad pinch arrives in Chrome/Firefox) anchored under the cursor, plus Zoom in/out/fit/today toolbar buttons, ported directly from the prototype's `setZoom`. Not verified in a running browser — reasoned through only, see the changelog entry's "Not verified" note. PROPOSED design, still NOT built, out of scope for the above: four header-tier presets (Day/Week/Month/Quarter, the header's own labels switching tier as the zoom level crosses a threshold), and the zoom level persisted to `localStorage` alongside the existing `expanded` state. See "Zoom" in Testing Decisions and the research update below for the pinch-event browser-compatibility evidence this proposal is based on.

**Scenarios stay disabled (PROPOSED to remain so, not reopened this round).** v1's correction disabling scenario auto-creation in favor of one working scenario is not revisited here. If what-if comparison is wanted back later, the direction proposed (not decided) is an explicit draft mode a user opts into, not something auto-created on edit the way v1's original (and the prototype's) `ensureScenario()` did.

**The right-hand panels (Risk, Workload, Efficiency gaps, Changes, Decision record, Compare) are unchanged (DECIDED).** Explicitly: "for now can be ignored... like not remove it just leave it be as is." Not evaluated, not redesigned, not in scope for this round.

## Testing Decisions

Unchanged from v1 for the scheduling core's existing surface (pure-function testing of topological ordering, cycle detection, recompute-on-change — see `v1/spec.md`). New surfaces this round would need the same treatment once built, none of it designed in detail yet:

- Each Blocked rule (once built) as a pure function: given a task graph and a candidate move, assert which rule fires, at which severity, and whether it blocks, warns, or flags.
- Rolled-up segment merging: given a set of overlapping child segments, assert the merged output, independent of rendering.
- Spill/commitment math: given a committed sprint and a position that runs past it, assert the spill state is reported without the task's sprint membership silently changing.
- Reason inheritance: given a chain of cascaded pushes, assert each downstream step's `causedBy` correctly traces back to the one human-authored reason that started the chain.
- Zoom-anchor math: given a zoom level change and a cursor/anchor position, assert the date under the anchor stays visually fixed (the same property the prototype's own `setZoom()` implementation already achieves, per this round's verification).

## Out of Scope

Everything in `v1/spec.md`'s Out of Scope list still applies unchanged (3D/4D, typed dependency relationships beyond finish-to-start, the Decision Record's real backend, a second lighter-density view, baseline-vs-actual variance, role-based views, agent/MCP read access). This round adds nothing new to the out-of-scope list and removes nothing from it — scenarios staying disabled is a PROPOSED continuation of an existing v1 decision, not a new exclusion.

## Further Notes

Per `AGENTS.md`'s rule that a reversed decision is named in writing where the reversal happens — all four below are reversals of specific `v1/spec.md` decisions. Items marked "would replace, if confirmed" are reversals of a PROPOSED direction against a DECIDED v1 behavior, not yet a settled reversal, since the v2 side of them isn't itself confirmed yet.

**Reversal: sprint membership is no longer purely "whichever sprint a step's end date falls in."** v1 decided this explicitly (`spec.md`: *"A step belongs to whichever sprint its own end date falls in — not whichever sprint its parent task is 'assigned to.'"*) and it's also the CTO doc's own R6. The reversal, DECIDED for the rendering half (sprints become calendar bands) and PROPOSED-only for the underlying commitment-vs-position split: a task's *commitment* (which sprint/parent it belongs to) and its *position* (where its current dates put it) become two separate facts, where today they're one and the same. This directly answers R6's own explicitly-deferred follow-up question from the source CTO doc ("how a task whose steps end in different sprints appears on each board and counts toward velocity") — the CTO doc deferred it, v1 inherited the deferral unresolved, and this is where it actually gets addressed, even though the exact commitment/position mechanics remain PROPOSED, not built.

**Reversal: the three-level Task → Stage → Step model's fixed *depth* is reversed; Stage itself is not.** v1: *"Work breaks into Task → Stage → Step, three levels"* with a stage path "locked at creation." DECIDED this round: subtasks nest to any depth. Stage stays as a concept (DECIDED, independently confirmed, and required by the CTO doc's R1/R2) — what's reversed is specifically the "exactly three levels, no deeper" constraint, not the existence of Stage as the middle one. Whether the deeper nesting mechanism is the generic `parentTask`/`subtasks` relation (PROPOSED) is itself contingent on an OPEN question above, so this reversal's *rendering/UX* half (arbitrary depth) is decided; its *data-model* half (which relation implements it) is not.

**Reversal: sprint rows default to collapsed, not expanded, on first load.** v1's fix (`what-changed.md`'s fix #11, `spec.md`'s own Further Notes) corrected a dead default-expanded list so that sprints actually opened by default. v2 reverses the *default state* itself — DECIDED: first load shows only the parent sprint rows (or bands, depending on how the OPEN sprint-row question above resolves) and the dependencies between them, with nothing pre-expanded. Implementation note, verified this round: `useRoadmapStore.ts`'s `persist()` config has no `version` field, so a returning user's already-persisted `expanded` array won't automatically pick up a new default — changing the default without a migration step would only affect first-time visitors, not existing ones. Worth deciding explicitly when this gets built, not discovering it after.

**Would replace, if confirmed: finish-to-start-only dependencies, with handoff and lag explicitly out of scope, against the proposed checkpoint-node handoff model.** v1's Out of Scope list explicitly excludes "typed dependency relationships beyond finish-to-start... and lead/lag offsets." The handoff-as-checkpoint-child PROPOSAL above doesn't actually introduce a new dependency type (it reuses finish-to-start against a child node), so it may not need to reverse this line at all — flagged here because it sits close to that boundary, not because it's confirmed to cross it.

**Would replace, if confirmed: "the red-line pattern does not transfer" (v1) against rule-driven clash states beyond date overlap.** v1's `spec.md` states directly: *"The dependency-line-turns-red-on-conflict pattern (Airtable) does not transfer to this engine, and that's deliberate... this engine's scheduler enforces the step chain on every recompute... so the state that check exists to catch cannot occur here."* That reasoning holds exactly as written for the *specific* case it was about (a step starting before its own predecessor finishes — still structurally impossible, unchanged). It does not cover the clash scenarios this round's Blocked-rules proposal names (same-person overlap, unowned overlap, spill, stage order), none of which the v1 scheduler prevents by construction. If the Blocked-rules table above is confirmed and built, it would replace v1's "no equivalent needed" conclusion with a real, rule-driven red-line condition for those cases specifically — not a reversal of the original Airtable-pattern reasoning, which is still correct for what it was actually about.

This is a first pass at the next iteration's ideation, same as v1 was — expect it to keep changing shape once the Open Questions above get answered and ticket work actually starts.
