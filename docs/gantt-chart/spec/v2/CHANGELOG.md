## 2026-10-21 — fix (incomplete — see correction above): orphaned connect-handle dots left behind when everything is collapsed

Found by the project owner collapsing the whole chart and seeing a scatter of floating circles and tangled lines with no bars attached (screenshot evidence, not reasoned out from code alone this time).

**Root cause:** a dependency edge whose true endpoint is hidden by a collapsed ancestor already correctly climbs to the nearest *visible* ancestor row for drawing the *line* (the "lines merge with the row tree" correction from v1). What this session's reactflow drag-to-connect rework didn't account for: the small, now-*visible* connect-handle dot (`AnchorNode`'s `Handle`s) rode along with that same climb — so every hidden step still rendered its own clickable connect dot at wherever its ancestor row landed, with no actual bar there for it to belong to. Invisible, pre-rework anchors never made this visible; real, clickable dots did.

**Fix:** `FlatGantt.tsx`'s `flowNodes` now only renders a visible, connectable `AnchorNode` when a uid's position resolves to its own real row (`resolveVisibleRow` found `rowByUid[uid]` directly) — a uid whose position was borrowed from a collapsed ancestor still gets an anchor node (edges still need a valid id to resolve against), but it renders invisible and non-connectable, the same shape already used for milestone anchors. Lines still correctly merge onto the ancestor exactly as before; only the per-uid connect-handle affordance is now gated on genuinely being visible.

`npm run build` passes, zero TypeScript errors. Not verified beyond that — no browser available in this environment; the fix is reasoned from the exact same `resolveVisibleRow`/`rowByUid` logic already established in this codebase, not observed rendered.

## 2026-10-21 — arbitrary-depth task nesting (parentTaskId, recursive row tree, per-row "Expand all")

Builds spec.md's "Nesting goes to any depth (DECIDED)" entry and the "Consequence of the above, for this app's mock/prototype engine specifically" paragraph: a task can have child tasks, recursively, to any depth — each child a full `TaskDef` in its own right (its own `path`/stages/steps/milestone/further children), not a Step-shaped node nested inside a Task-shaped one. This is the data-model/rendering half only — **rolled-up segments on a collapsed parent** (User Story 30, PROPOSED in spec.md, not yet detailed enough to build) are explicitly NOT part of this entry: a collapsed (or expanded-but-childless-of-its-own-bar) parent task behaves exactly like today's uid-less row — no bar — not worse, just not the fancier version yet.

**Data model, `app/src/lib/engine/types.ts`:** `TaskDef` gains `parentTaskId?: string | null`. Named `parentTaskId` rather than the real Strapi schema's `parentTask` because this mock engine already stores every other relation as a plain id reference, not a relation object (e.g. the existing `milestone: string | null` field for the `milestone` relation) — same convention, not a new one. Absent/`null` means a root task, same as every task today.

**Scheduling rollup, `app/src/lib/engine/schedule.ts`:** `computeSchedule()`'s per-task rollup is now a memoized recursive function (`rollupFor`), not a single `ctx.tasks.forEach` pass — a parent's rollup can depend on its children's rollups, and `ctx.tasks` (flattened from seed + userTasks) has no guaranteed parent-before-child order. A task with children but no steps of its own rolls up to the min-start/max-end (and OR'd `moved`, max `slip`) across its children's own rollups, recursively. A task with **both** its own steps and children combines the two: start/end span the wider of the two sides, `moved` is OR'd, `slip` takes the max — documented inline as "the more-attention-worthy side" rather than silently favoring one. A task with neither falls back to the existing plain-bar-dates rollup, unchanged. A `visiting` set guards against a corrupt/cyclic `parentTaskId` chain recursing forever (defensive only — no legitimate way to form one, see the inline comment).

**Row tree, `app/src/components/FlatGantt/layout.ts`:** `buildRows()`'s task-row construction is now a recursive `buildTaskSubtree(taskId, depth, rowId, sprintId, filterToSprint, visited)` function instead of a flat loop. A **root** task is still bucketed into whichever sprint its own steps/rollup end date falls in (unchanged top-level behavior, now gated on `!t.parentTaskId` so a child task doesn't also show up as an independent top-level row in its own right). A **child** task renders nested under its parent's row at `depth + 1` (row id `${parentRowId}::${childId}`, extending the existing `${sprintId}::${taskId}` convention one more segment per nesting level — `expanded`'s existing string-array/localStorage mechanism needed no changes, it already treats row ids as opaque strings) and shows its own full step list, un-bucketed by sprint (the "task whose steps end in different sprints" multi-bucketing problem this would otherwise reintroduce one level down is the same already-known, separately-tracked issue named in spec.md's Baseline Fixes table, not re-solved here for nested tasks either). Ordering choice, documented inline: a task's own step rows render before its child-task rows. A task's own row only gets a `uid` (i.e. only draws its own bar) when it is a true leaf — no steps, no children — extending the exact rule the pre-nesting code already used for a plain-bar task; a parent (whether via steps or children) shows its bars on the rows nested beneath it instead, same "no bar on a `uid`-less row" behavior the chart already has today. A `visited` set guards the recursion against a cyclic `parentTaskId` chain the same way `schedule.ts`'s rollup does.

**Per-row "Expand all" (User Story 31):** new `collapsibleDescendantIds(ctx, sched, rootId)` in `layout.ts` runs `buildRows` to a fixed point (growing the `expanded` set until no new collapsible row id appears, capped at 64 iterations defensively) to discover a subtree's full collapsible-id list even for currently-collapsed descendants, then filters to `rootId` and its prefix-matched descendants (row ids are parent-prefixed by construction, see above). New store action `expandSubtree(ids)` in `useRoadmapStore.ts` **merges** ids into the existing `expanded` array (unlike the existing global `expandAll(ids)`, which replaces it wholesale) so expanding one row's branch doesn't collapse whatever else the user had open elsewhere. `FlatGantt.tsx`'s `RowLabel` gained a second small icon button (⇊, tooltipped "Expand this row and everything beneath it") next to the existing per-row +/− toggle, on every collapsible row — additive, the existing global "Expand all" toolbar button is untouched.

**`allLinkableUids` / milestone-gating anchors (`FlatGantt.tsx`):** tightened to match the new uid-assignment rule exactly — a task is only pushed as its own linkable id when it has neither steps nor children, mirroring `buildRows`' leaf-only `uid` rule above (previously this only checked "no steps," which would have made a steps-less parent-with-children wrongly linkable by an id no row actually exposes).

**Mock data, `app/src/lib/mock-data/seed.v1.json` + `tasks.ts`:** `SeedTask` gained optional `parentTaskId`; `tasks.ts`'s `BASE_TASKS` mapping threads it through (`t.parentTaskId ?? null`). One small illustrative example added: `OAK-200` "Regional rollout coordination" (root, has its own planning step), `OAK-201` "EU rollout" (`parentTaskId: "OAK-200"`, has its own design step), `OAK-202` "EU rollout - translations" (`parentTaskId: "OAK-201"`, has its own development step) — depth-2 nesting, and both `OAK-200`/`OAK-201` exercise the "own steps AND children" combined-rollup case. No existing task/link/milestone data touched.

**Not verified:** no browser is available in this environment. `npm run build` passes with zero TypeScript errors (confirmed by actually running it, not assumed). Not observed running: whether `OAK-200`/`OAK-201`/`OAK-202` actually render, collapse, and expand correctly at all three depths in the live chart; whether the new per-row ⇊ button visually fits next to the existing +/− toggle without crowding the row label at the current `LABEL_W`; and whether a returning user's already-persisted `expanded` array (pre-dating this change) round-trips through `localStorage` correctly against the new, deeper row ids — the `expanded` field's shape (`string[]`) and `partialize` inclusion are unchanged, so old ids simply won't match anything new and new ids simply weren't in the old array, which should degrade to "nothing new auto-expands," not a crash, but this was reasoned through, not run.

## 2026-10-21 — critical/expired risk gets a diagonal-hatch fill (styling only, not the "spill" mechanic)

Closes the specific visual gap named by the owner's mockup: a task past a hard deadline (gating task ending after its milestone's due date) should render with a solid diagonal-hatch fill across the whole bar, not just a colored/dashed outline. This is the **styling-only** half of the mockup's risk-visualization language — it reuses the exact same existing `sev: "critical" | "expired"` detection in `app/src/lib/engine/schedule.ts` (confirmed: the only place those severities are set is the gating-task-vs-milestone-due-date check, ~line 361; untouched by this change) and changes only how an already-detected risk renders. The "spill" mechanic — a task shown inside its committed sprint, hatched specifically for the overrun portion — is explicitly NOT part of this entry; it still needs the "committed sprint vs. current position" data-model decision tracked in `todo.md`'s "Commitment/position data shape" item, not yet started.

**`app/src/components/FlatGantt/FlatGantt.tsx`:** a new SVG `<pattern id="crithatch">` added to `<defs>`, alongside the existing `revhatch` pattern (the proven precedent for "diagonal hatch overlay on a bar" in this stack, used for the `review` step overlay). `crithatch` is its own pattern, not a reuse of `revhatch`, because a step can be both a review step and past a hard deadline at once and the two need to stay visually distinguishable: `revhatch` is white stripes with no tint (reads against whatever the bar's base color is), `crithatch` is a translucent red wash (`var(--crit)` at 18% fill opacity) plus red diagonal stripes at the opposite rotation (`rotate(45)` vs. `revhatch`'s `rotate(-45)`) so the two patterns don't visually merge into one when both apply to the same bar.

**`app/src/components/FlatGantt/Bar.tsx`:** when `outline === "critical" || outline === "expired"` (the same `outlineSeverity()` check already driving the dashed stroke), a new overlay `<rect>` is rendered with `fill="url(#crithatch)"`, sized to `pos.w`/`pos.w` same as the existing `review` hatch overlay rect, and placed directly after it in the JSX (so paint order is: body → review hatch → critical hatch → label text → info dot → resize grip). The existing dashed red outline (`stroke`/`strokeDasharray="4 2"` on `rect.body`, the prior round's "broken-dashed-red" fix) was **kept, not replaced** — it's additive styling on top of an already-established signal, not a reason to remove it.

**Composes with the live drag-cap indicator:** `useBarDrag.ts`'s `paintFrame` was re-read to confirm it only ever queries `rect.body` (by class) and `[data-grip]`/`[data-drag-label]` (by attribute) to imperatively set `stroke`/`stroke-dasharray` during a drag-cap violation — it never touches a second overlay `<rect>`, so the new `crithatch` overlay rect is unaffected by and doesn't interfere with that mechanism.

**Not verified:** no browser is available in this environment. `npm run build` passes with zero TypeScript errors. Not observed running: how the red hatch actually looks, whether it reads clearly at small bar sizes (narrow steps), and whether it visually competes with the review hatch when both apply to the same bar — the two patterns' differing tint/rotation were reasoned through to stay distinguishable but not seen rendered.

## 2026-10-21 — sprint calendar bands (additive band only, row question still open)

Builds the DECIDED half of spec.md's "Sprints render as calendar bands, flat bars underneath" entry: a tinted full-height column band per real sprint, drawn directly on the calendar/date-axis area. Explicitly does NOT touch whether a sprint also keeps its own collapsible row in the tree — that's still OPEN per `todo.md`'s first bullet, and `app/src/components/FlatGantt/layout.ts`'s `buildRows()` sprint-row grouping/collapsing logic was not modified at all. This is the additive-band-only scope named in `todo.md`.

**`app/src/components/FlatGantt/FlatGantt.tsx`:** a new `sprintBands` array is built the same way `weekendBands` already is — iterating `sched.sprints` (filtering out `UNSCHEDULED_ID`, imported from `layout.ts`, the same synthetic bucket other sprint-iterating code in this file already excludes), computing each band's pixel range via the existing `xForDate(T0, date, dw)` helper so it recomputes correctly under the live zoom state (`dw`) from the prior round's zoom work — nothing hardcoded. Each sprint gets a full-height `<rect>` (`y={AXIS_H}` to `svgHeight`) in an alternating two-tone fill (`i % 2 ? "#eef2ff" : "#e0e7ff"`), ported directly from `prototype/app.js`'s own sprint-axis rendering (`i % 2 ? "#eef2ff" : "#e0e7ff"`, confirmed by reading that file), plus a left-aligned `<text>` label with the sprint's name. The label's `y` is deliberately placed below the first sprint-group header row's own height (`AXIS_H + SPRINT_H + 12`, not `AXIS_H + 12`) — the existing per-row highlight rect (`rows.map(...)`'s `fill={row.kind === "sprint" ? **Paint order:** `{sprintBands}` is rendered in the JSX tree immediately before `{weekendBands}`, both of which sit right after the SVG's `<defs>` and before the "as of" marker, axis labels, row-highlight rects, milestone diamonds, and bars — i.e. sprint bands paint first (bottom-most in SVG z-order), underneath weekend shading, the existing sprint-row highlight rects, milestone diamonds, bars, and dependency/link lines, exactly matching how `weekendBands` already establishes "paint first" as the convention for background layers in this file.

## 2026-10-21 — pinch-to-zoom port: continuous zoom via ctrl/meta+wheel, anchored under the cursor

Ports the prototype's proven zoom mechanism (`prototype/app.js`'s `setZoom`, ~line 2605) into the Next.js app, per owner feedback that pinch-to-zoom on a trackpad must work and the port currently had none. Scope was deliberately narrow — the still-open "four header-tier presets" proposal in `todo.md` is explicitly NOT part of this entry.

**`DW` goes from a module constant to React state:** `app/src/components/FlatGantt/layout.ts` no longer exports `DW`; it exports `DEFAULT_DW = 36` (the port's already-decided baseline, not the prototype's `12`) as the initial value only. `xForDate(t0, date)` and `barPosForRow(t0, row, start, durationDays)` both gained a trailing `dw: number` parameter instead of reading the old constant. Every call site was updated to pass the live value: `app/src/components/FlatGantt/FlatGantt.tsx` (axis/weekend-band/bar-position math, `flowNodes`/`flowEdges` memo deps), `app/src/components/FlatGantt/useBarDrag.ts` (`opts.dw`, threaded through `paintFrame` and the drag's pixel→day conversion), and `app/src/components/FlatGantt/Milestone.tsx`'s `MilestoneDiamond` (new `dw` prop). `DependencyEdges.tsx` was read and confirmed to have no `DW` dependency at all (its `minZoom`/`maxZoom`/`zoomOnScroll`/`zoomOnPinch` reactflow settings are independent of day-width) — left untouched.

**Zoom state + interaction, `FlatGantt.tsx`:** `dw` is now `useState(DEFAULT_DW)`. `setZoom(nw, anchorClientX?)` clamps to `[4, 40]`, no-ops if unchanged, computes the date-under-cursor (`dayAt`) from the pre-zoom layout, stores it in a ref, then calls `setDw`. A `useLayoutEffect` keyed on `dw` restores `scrollRef.current.scrollLeft` from that stashed anchor immediately after React commits the new layout but before the browser paints — this is the one spot the port couldn't copy the prototype's synchronous "mutate DW, call render(), write scrollLeft" sequence directly, since the new layout only exists once a render triggered by the state update has actually happened. A native (non-React) `wheel` listener is attached to the scrollable chart container (`scrollRef`) via `addEventListener(..., { passive: false })` in a `useEffect`, gated on `e.ctrlKey || e.metaKey` (how a trackpad pinch arrives in Chrome/Firefox) and calling `e.preventDefault()` — required because JSX's `onWheel` is always passive and can't block the browser's own page-zoom. Toolbar gained "Zoom out" / "Zoom in" / "Zoom to fit" / "Zoom to today" buttons (same `Button size="xs" variant="default"` style as the rest of the toolbar) plus a live `%` readout, all in the existing `Toolbar` function.

**Not verified:** no browser is available in this environment. `npm run build` passes with zero TypeScript errors, and every `DW` consumer was traced and updated by reading the actual code, but actual pinch/ctrl+wheel behavior, whether the cursor-anchoring math feels right, and whether the scroll-restore `useLayoutEffect` actually eliminates a visible jump were all reasoned through, not observed running.

## 2026-10-21 — baseline fixes, round 1: four pre-existing v1 gaps from spec.md's "Baseline fixes before new work" table

No tickets exist against v2 yet — this round closes four specific rows of spec.md's "Baseline fixes before new work" table directly, ahead of ticket breakdown, per explicit instruction. Each row's status is updated in place in `spec.md` rather than removed, naming this entry.

**Resize grip / connect handle overlap (row 1):** `app/src/components/FlatGantt/DependencyEdges.tsx` adds a new `HANDLE_RIGHT_PAD` (6px) constant. `app/src/components/FlatGantt/FlatGantt.tsx`'s `flowNodes` memo widens every linkable anchor node's box by that amount past the bar's real right edge, so the Position.Right source `Handle` (CSS `right: -4px` relative to the node's own box) lands a few px clear of `Bar.tsx`'s 6px resize grip (`x = pos.w - 6`) instead of directly on top of it. Only the anchor node's own invisible box grows; `Bar.tsx`'s grip and the bar's real rect are untouched. Verified by reading code that the target handle (`Position.Left`, the bar's left edge) has no equivalent collision — there's no grip on that edge — so it was left alone.

**Connection dots drifting during a live drag (row 2):** `app/src/components/FlatGantt/useBarDrag.ts`'s `paintFrame` now also repositions each dragged/cascaded bar's reactflow anchor-node DOM element every pointermove frame, the same imperative way it already repositions the bar/grip. Investigated reactflow's actual rendered node markup (`@reactflow/core`'s `NodeWrapper`, confirmed in `node_modules/@reactflow/core/dist/esm/index.mjs`) rather than guessing: each node renders as a real `.react-flow__node[data-id="<uid>"]` div with its position driven by an inline `style.transform`, which `paintFrame` can safely read/write directly — no custom attribute needed, `data-id` already equals the bar's own uid. A later React re-render (on drag commit) overwrites this back to the correct computed value, the same reconciliation already relied on for the plain-SVG bar/grip elements. True live tracking was used instead of the opacity/hide fallback, since the mechanism turned out not to fight reactflow at all. The anchor's width is also kept in sync with `pos.w + HANDLE_RIGHT_PAD` during a resize, so the handle offset stays correct mid-resize too.

**No visual distinction between removable and non-removable lines (row 7, "No clear indicator of which lines are removable..."):** `DependencyEdges.tsx`'s `DependencyEdge` now defaults a non-clash line's stroke/dash based on `data.removable`: a removable (single, unambiguous) dependency link now defaults to a darker solid stroke (`#64748b`), a non-removable line (a merged multi-link group, where a click can't mean one specific link) defaults to a lighter dashed stroke (`#cbd5e1`, `"2 3"`). Milestone connectors are unaffected — they already always pass an explicit `stroke`/`dashed` (`m?.color` / `"4 3"`, or clash red), so these new fallbacks never apply to them; they were already visually distinct from a plain dependency line before this change. Clash styling (`g.clash`/`isGatingRisk`) still wins whenever set, since it always supplies an explicit `data.stroke`/`data.dashed` that these fallbacks never override.

**Frozen drag gives no explanation of which limit it hit (row 5):** `useBarDrag.ts`'s `handleMove` now derives a short `reason` string (same priority order as the existing `exceeds` check: milestone gate, then chart edge, then task span) whenever a drag freezes, e.g. `"Capped at milestone deadline (DD Mon)"`, `"Capped at chart edge"`, or `"Capped — would delay a later step in this task"`. `FlatGantt.tsx` adds a permanently-rendered-but-hidden `<g data-drag-label="1">` (rect + text) inside the chart's SVG; `paintFrame` toggles its visibility and sets its position/text attributes imperatively, live, the same query/setAttribute pattern used for the rest of this drag loop — no React state, no per-frame element creation/removal. Hidden unconditionally on drag end (`handleUp`) as a safety net, in case a drag is released while still frozen.

**Not verified:** no browser is available in this environment; all four of the above are visual/interaction fixes. `npm run build` passes with zero TypeScript errors; the handle offset, anchor-node DOM structure (`@reactflow/core`'s rendered output), and drag-label logic were verified by reading reactflow's actual source/CSS and this codebase's render tree, not by seeing them run.
